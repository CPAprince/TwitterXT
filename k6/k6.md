# k6 Load Testing Guide (TwitterXT)

This directory contains load and stress testing scenarios built with **[k6](https://k6.io/)** and the **`xk6-sql`** extension to simulate realistic user behavior on the TwitterXT platform.

---

## 📋 Scenarios Overview

All 4 scenarios utilize actual application data pre-loaded from MySQL (users, tweets, profiles) and measure granular response times per route using custom `endpoint` tags.

| Scenario | Load Profile | Default VUs | Duration | Key Journey Steps |
| :--- | :--- | :--- | :--- | :--- |
| **`TwitterSeedSessions.js`** | **Parallel Session Warmer** (Pre-test utility) | 5 VUs | Shared iterations | Authenticates unauthenticated users in 5 parallel streams (`POST /api/token`) to populate `app.refresh_tokens` for future load tests. |
| **`TwitterGPTtest5sql.js`** | **Mixed Standard Profile** (Typical user activity) | 5 VUs | ~8m 10s | Anonymous feed scroll ➔ Login (JWT) ➔ Authenticated feed ➔ Browse 1–3 profiles ➔ 0–2 likes |
| **`TwitterGPTtest5sqlPoolRefresh.js`** | **High-Throughput User Pool & Token Refresh** (Read/Like Heavy) | 8 VUs | ~8m 10s | Pre-authenticated pool (min 1,000 users). Instant `POST /api/token/refresh` (~5-10ms) instead of bcrypt login. |
| **`TwitterGPTtest5sqlPostRefresh.js`** | **High-Throughput Full Cycle with Tweet Posting** (Recommended) | 8 VUs | ~8m 10s | Pre-authenticated pool + **17% chance of posting real tweets** (`POST /api/tweets`). Triggers Redis feed cache invalidation, async RabbitMQ AI moderation, and dynamic feed updates. |
| **`TwitterGPTtest5sqlFEEDS.js`** | **Read-Only / Lurker Load** (Heavy read traffic) | 5 VUs | ~8m 10s | Anonymous deep feed pagination (probabilistic up to 15 pages) ➔ Browse author profiles. **Zero logins, zero likes, zero database writes**. |
| **`TwitterGPTtest5sqlPOST.js`** | **Realistic Social Flow** (Production traffic mix) | 5 VUs | ~8m 10s | Feed scroll ➔ Login ➔ Profiles ➔ **17% probability of posting a new tweet** ➔ Likes. Exercises message queue, async moderation, and database writes. |
| **`TwitterGPTtest5sqlPOSTer.js`** | **Content Soak / Flood** (High-volume content creation) | 6 VUs | ~1h 02m | Login ➔ **Batch tweet posting loop (3 to 50 tweets per iteration)**. Long-running soak test targeting RabbitMQ queue, AI moderation workers, and DB write throughput. |

## ⚙️ Prerequisites

### 1. Running Application Stack in Production Mode
For accurate benchmark results without overhead from the Symfony WebProfiler, debug listeners, SQL query logging, or file watchers, run the stack in production mode:
```bash
# Stop running dev containers:
make stop

# Build and start in production mode (APP_ENV=prod, APP_DEBUG=0, OPcache enabled, 5 persistent FrankenPHP workers):
make startprod
```

> [!TIP]
> After finishing load tests, switch back to development mode with:
> ```bash
> make stop
> make startdev
> ```

* **Database**: MySQL is exposed on `127.0.0.1:3306` (user: `app`, password: `!ChangeMe!`, database: `app`).
* **API Base URL**: `https://localhost` (`insecureSkipTLSVerify: true` is configured to accept Caddy's local self-signed TLS certificates).
* **Test Data**: The database must contain seeded accounts in `app.users` with password `Pa$$word1`, and existing tweets in `app.tweets`.

### 2. `xk6-sql` Extension Requirement
> [!IMPORTANT]
> The standard official `k6` binary does not include SQL drivers. These scenarios import `k6/x/sql` and `k6/x/sql/driver/mysql` to query test fixtures directly into memory during test initialization.

**Options to run:**
* **Build locally with `xk6`**:
  ```bash
  go install go.k6.io/xk6/cmd/xk6@latest
  xk6 build --with github.com/grafana/xk6-sql
  ./k6 run k6/TwitterGPTtest5sql.js
  ```
* **Run via Docker with `xk6-sql`**:
  ```bash
  docker run --rm -i --net=host -v ${PWD}:/scripts grafana/k6:latest-with-sql run /scripts/k6/TwitterGPTtest5sql.js
  ```

## 🧠 Why Up to 5–6 Virtual Users (VUs)?

The default concurrency is intentionally capped at **5–6 VUs**. This is based on specific architectural considerations:

1. **Authentication CPU Overhead (Argon2id / Bcrypt)**:
   * The `POST /api/token` route executes password hash verification via `password_verify()`.
   * Key derivation functions are intentionally CPU-heavy to prevent brute-force attacks.
   * Running 50–100 VUs with frequent logins would saturate host CPU purely on cryptographic operations, creating an artificial bottleneck unrelated to application business logic (feeds, tweets, profiles).
2. **High Continuous RPS (Zero Think Time)**:
   * The scripts configure `THINK_TIME_MIN = 0` and `THINK_TIME_MAX = 0`.
   * With zero sleep between requests, 5–6 continuous VUs generate **hundreds of requests per second (RPS)**, mirroring the traffic load of hundreds of concurrent human users browsing with typical 2–5 second reading pauses.
3. **In-Memory SQL Pre-Loading**:
   * During the `init` stage, each VU loads between 10,000 and 100,000 records (emails, profile UUIDs, tweet IDs) into memory. Capping VUs keeps the k6 memory footprint lean and stable.

## 🚀 Execution Commands

### Scenario 1: Mixed User Activity (`TwitterGPTtest5sql.js`)
Simulates regular user behavior: browsing feeds, authenticating, viewing author profiles, and liking tweets.

```bash
# Standard execution with configured stages (~8m 10s):
k6 run k6/TwitterGPTtest5sql.js

# Quick 1-minute smoke test with 3 VUs:
k6 run --vus 3 --duration 1m k6/TwitterGPTtest5sql.js

# Target 6 VUs for 3 minutes:
k6 run --vus 6 --duration 3m k6/TwitterGPTtest5sql.js
```

Focuses on feed pagination (`page=1`, `page=2`, `page=3`, `page>=4`) and profile bio / tweets retrieval without authentication. Excellent for inspecting database read indexes, Doctrine N+1 queries, and cache efficiency.

### Scenario 3: Mixed Social Activity with Posting (`TwitterGPTtest5sqlPOST.js`)
Simulates realistic production traffic: 83% read and like operations, with a ~17% probability of creating a new tweet using real text samples from the database. Exercises the full pipeline: Controller ➔ Database ➔ RabbitMQ ➔ Messenger Worker ➔ AI Moderation ➔ Mercure SSE.

```bash
# Standard execution (~8m 10s):
k6 run k6/TwitterGPTtest5sqlPOST.js

# Run with 5 VUs for 5 minutes:
k6 run --vus 5 --duration 5m k6/TwitterGPTtest5sqlPOST.js
```

### Scenario 4: High-Volume Tweet Creation / Content Soak (`TwitterGPTtest5sqlPOSTer.js`)
Aggressive content generation: each VU logs in and repeatedly posts batches of 3–50 tweets in a loop. Configured by default as a 1-hour soak test to detect memory leaks, queue backpressure, and worker degradation under continuous writes.

```bash
# Standard 1-hour soak test:
k6 run k6/TwitterGPTtest5sqlPOSTer.js

# Short burst stress test (6 VUs for 3 minutes):
k6 run --vus 6 --duration 3m k6/TwitterGPTtest5sqlPOSTer.js
```

### Scenario 5 (Recommended): Pre-authenticated Pool & Token Refresh (`TwitterGPTtest5sqlPoolRefresh.js`)
Eliminates the ~700ms CPU penalty of password verification on every iteration.
* **Intelligent Seeding**: In `setup()`, checks `app.refresh_tokens` for active tokens (`valid > NOW()`). If DB has $\ge$ `MIN_LOGGED_IN_USERS` (e.g. 4,621 users), it uses all of them without new logins. If fewer (e.g. 700 available and 1,000 required), it logs in the missing 300 users once during setup and saves their refresh tokens to the database for subsequent runs.
* **High Throughput**: Access tokens are refreshed via fast `POST /api/token/refresh` (~5–12ms, no bcrypt) and cached per VU for 14 minutes. Sustains **850+ req/s** with sub-10ms average latency (over 418,000 requests in 8 minutes with 0.00% failure rate)!

```bash
# Standard execution with 8 VUs stages (~8m 10s):
k6 run k6/TwitterGPTtest5sqlPoolRefresh.js

# Custom pool size (e.g. minimum 2000 users) and 8 VUs for 3 minutes:
MIN_LOGGED_IN_USERS=2000 k6 run --vus 8 --duration 3m k6/TwitterGPTtest5sqlPoolRefresh.js

# Quick 1-minute benchmark with 8 VUs:
k6 run --vus 8 --duration 1m k6/TwitterGPTtest5sqlPoolRefresh.js
```

### Scenario 6 (Recommended): Full Cycle with Tweet Posting & Cache Invalidation (`TwitterGPTtest5sqlPostRefresh.js`)
Combines the high-throughput token refresh mechanism with real content creation and dynamic feed cache invalidation.
* **Real Content Seeding**: Pre-loads 10,000 real tweet text samples using a full UTF-8 byte decoder (`utf8BytesToString()`) preserving emojis, Cyrillic, and formatting.
* **Cache Invalidation & Queue Stress**: With a configurable probability (default **17%** per iteration), authenticated users create new tweets via `POST /api/tweets`. This triggers:
  1. MySQL `INSERT` into `app.tweets`.
  2. Redis tag invalidation (`user_tweets_{userId}`) via `CreateTweetCommandHandlerDecorator`.
  3. Async messaging to RabbitMQ for AI moderation workers.
  4. Subsequent feed browsing fetches updated, fresh content.
* **Deep Feed Pagination**: Supports deep probabilistic feed pagination up to 15 pages (`FEED_PAGES=15`).

```bash
# Standard 8-minute benchmark with 8 VUs:
k6 run k6/TwitterGPTtest5sqlPostRefresh.js

# Custom posting probability (e.g. 25% chance of tweet creation per iteration):
POST_PROBABILITY=25 k6 run k6/TwitterGPTtest5sqlPostRefresh.js

# Quick 1-minute smoke test with 5 VUs:
k6 run --vus 5 --duration 1m k6/TwitterGPTtest5sqlPostRefresh.js
```

### Utility: Parallel User Session Warmer (`TwitterSeedSessions.js`)
Dedicated preparation utility to authenticate users and pre-populate `app.refresh_tokens` before running load tests.
* **5 Parallel Worker Streams**: Uses `shared-iterations` across 5 VUs to saturate all 5 FrankenPHP workers without queuing.
* **Zero Overhead**: Does not fetch feeds, view profiles, or toggle likes; purely executes `POST /api/token`.
* **One-Time Run**: Once sessions are created, they remain valid in the database for 7 days (`valid > NOW()`).

```bash
# Authenticate and save 5,000 users into app.refresh_tokens:
k6 run k6/TwitterSeedSessions.js

# Authenticate 10,000 users:
TARGET_USERS=10000 k6 run k6/TwitterSeedSessions.js

# Quick smoke test with 100 users:
TARGET_USERS=100 k6 run k6/TwitterSeedSessions.js
```

## 📊 Metrics & Thresholds

All scenarios tag requests with a specific `endpoint` identifier for detailed performance tracking:

| `endpoint` Tag | Target HTTP Route | Description |
| :--- | :--- | :--- |
| `Login` | `POST /api/token` | User authentication & JWT retrieval (~700ms bcrypt) |
| `TokenRefresh` | `POST /api/token/refresh` | Lightweight access token renewal (~5–10ms indexed DB lookup) |
| `tweets_page1` | `GET /api/tweets?limit=50&page=1` | Main feed, first page |
| `tweets_page2` | `GET /api/tweets?limit=50&page=2` | Feed scroll, second page |
| `tweets_page3` | `GET /api/tweets?limit=50&page=3` | Feed scroll, third page |
| `tweets_page4plus` | `GET /api/tweets?limit=50&page>=4` | Deep feed pagination (higher offset queries) |
| `ProfileNameBio` | `GET /api/profiles/{id}` | User profile metadata |
| `ProfileFeed` | `GET /api/profiles/{id}/tweets` | Specific user's tweet history |
| `Like` | `POST /api/tweets/{id}/likes/toggle` | Like / unlike toggle action |
| `CreateTweet` | `POST /api/tweets` | Tweet creation endpoint |

### Success Thresholds:
* **`http_req_failed`**: `< 1%` failure rate (`rate < 0.01`).
* **`http_req_waiting` (TTFB)**: `p(95) < 10000ms`.
* **`http_req_duration{endpoint:...}`**: `p(95) < 10000ms` individually tracked per endpoint.
