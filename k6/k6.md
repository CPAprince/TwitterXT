# Руководство по нагрузочному тестированию k6 (TwitterXT)

В данной директории собраны сценарии нагрузочного и стресс-тестирования на базе **[k6](https://k6.io/)** с расширением **`xk6-sql`** для симуляции реального пользовательского поведения в приложении TwitterXT.

---

## 📋 Обзор сценариев

Все 4 сценария используют реальные данные из базы данных MySQL (пользователи, твиты, профили) и измеряют время отклика конкретных эндпоинтов через теги `endpoint`.

| Сценарий | Профиль нагрузки | VU (по умолчанию) | Длительность | Основные действия |
| :--- | :--- | :--- | :--- | :--- |
| **`TwitterGPTtest5sql.js`** | **Mixed Standard Profile** (Смешанный пользовательский поток) | 5 VU | ~8 мин 10 сек | Анонимный скролл ленты ➔ Логин (JWT) ➔ Авторизованная лента ➔ Просмотр 1–3 профилей ➔ 0–2 лайка |
| **`TwitterGPTtest5sqlFEEDS.js`** | **Read-Only / Lurker** (Нагрузка на чтение) | 5 VU | ~8 мин 10 сек | Анонимное глубокое чтение ленты (до 7 страниц) ➔ Просмотр профилей. **Без логина и без записей в БД**. |
| **`TwitterGPTtest5sqlPOST.js`** | **Realistic Social Flow** (Реалистичная активность с твитами) | 5 VU | ~8 мин 10 сек | Лента ➔ Логин ➔ Профили ➔ **17% вероятность публикации нового твита** ➔ Лайки. Нагружает очередь модерации и БД. |
| **`TwitterGPTtest5sqlPOSTer.js`** | **Content Soak / Flood** (Массовая публикация контента) | 6 VU | ~1 час 2 мин | Логин ➔ **Цикл публикации твитов пачками (от 3 до 50 твитов подряд)**. Длительный стресс-тест очереди RabbitMQ, AI-модерации и записи в БД. |

## ⚙️ Требования и окружение (Prerequisites)

### 1. Запущенный стек сервисов
Перед запуском тестов убедитесь, что инфраструктура и бэкенд запущены:
```bash
docker compose up -d
docker compose ps
```

* **База данных**: порт `127.0.0.1:3306` должен быть доступен (пользователь `app`, пароль `!ChangeMe!`, база `app`).
* **API URL**: `https://localhost` (в скриптах включен параметр `insecureSkipTLSVerify: true` для работы с самоподписанным сертификатом Caddy).
* **Тестовые данные**: в таблице `app.users` должны быть пользователи с паролем `Pa$$word1`, а в `app.tweets` — твиты для сидинга списков чтения/лайков.

### 2. Поддержка `xk6-sql` в k6
> [!IMPORTANT]
> Стандартный бинарник `k6` не содержит драйверов для подключения к SQL-базам данных. Сценарии используют модуль `k6/x/sql` и драйвер `k6/x/sql/driver/mysql` для выборки тестовых данных в память на этапе инициализации.

**Варианты запуска:**
* **Собрать k6 с поддержкой SQL локально**:
  ```bash
  go install go.k6.io/xk6/cmd/xk6@latest
  xk6 build --with github.com/grafana/xk6-sql
  ./k6 run k6/TwitterGPTtest5sql.js
  ```
* **Использовать подготовленный Docker-образ**:
  ```bash
  docker run --rm -i --net=host -v ${PWD}:/scripts grafana/k6:latest-with-sql run /scripts/k6/TwitterGPTtest5sql.js
  ```

## 🧠 Почему используется до 5–6 виртуальных пользователей (VUs)?

При тестировании задан лимит **5–6 виртуальных пользователей**. Это осознанное архитектурное решение, обусловленное следующими факторами:

1. **CPU-нагрузка при аутентификации (Argon2id / Bcrypt)**:
   * Эндпоинт `POST /api/token` выполняет сверку хеша пароля через `password_verify()`.
   * Хеширование намеренно замедлено криптографическими алгоритмами (защита от брутфорса).
   * При высоком параллелизме (например, 50–100 VU, выполняющих частые логины) процессор сервера утилизируется на 100% исключительно генерацией и проверкой хешей, создавая искусственное "бутылочное горлышко", которое не отражает реальную производительность прикладных API (ленты, профили, твиты).
2. **Интенсивность запросов (RPS) без пауз**:
   * В скриптах параметры пауз между действиями установлены в `THINK_TIME_MIN = 0` и `THINK_TIME_MAX = 0`.
   * 5–6 пользователей, безостановочно отправляющих запросы, генерируют суммарно **сотни HTTP-запросов в секунду (RPS)**, что эквивалентно поведению сотен обычных пользователей с естественными паузами в 2–5 секунд.
3. **Объем предзагрузки данных (SQL Preload)**:
   * На этапе инициализации каждый VU загружает в память от 10 000 до 100 000 записей (email, UUID профилей, ID твитов). Большое количество VU приведет к высокому расходу оперативной памяти процессом k6.

## 🚀 Команды для запуска сценариев

### Сценарий 1: Общее поведение (`TwitterGPTtest5sql.js`)
Имитирует типовой рабочий день: пользователи читают ленту, авторизуются, листают профили и ставят лайки.

```bash
# Стандартный прогон со встроенными stages (~8 мин):
k6 run k6/TwitterGPTtest5sql.js

# Быстрый смоук-тест на 1 минуту с 3 VU:
k6 run --vus 3 --duration 1m k6/TwitterGPTtest5sql.js

# Запуск с 6 VU на 3 минуты:
k6 run --vus 6 --duration 3m k6/TwitterGPTtest5sql.js
```

---

### Сценарий 2: Нагрузка на чтение (`TwitterGPTtest5sqlFEEDS.js`)
Чистое чтение ленты с пагинацией (1-я, 2-я, 3-я и последующие страницы) и чтение страниц профилей авторов. Отлично подходит для проверки кэширования, N+1 в Doctrine и индексов MySQL.

```bash
# Стандартный прогон (~8 мин):
k6 run k6/TwitterGPTtest5sqlFEEDS.js

# Прогон с 5 VU на 2 минуты:
k6 run --vus 5 --duration 2m k6/TwitterGPTtest5sqlFEEDS.js
```

---

### Сценарий 3: Смешанный продакшн-поток с твитами (`TwitterGPTtest5sqlPOST.js`)
Симулирует реальную социальную сеть: 83% действий — чтение и лайки, а ~17% пользователей создают новый твит с текстом из предварительно отобранной базы. Нагружает всю цепочку: HTTP -> Controller -> DB -> RabbitMQ -> Worker -> AI-модерация -> Mercure.

```bash
# Стандартный прогон (~8 мин):
k6 run k6/TwitterGPTtest5sqlPOST.js

# Запуск с 5 VU на 5 минут:
k6 run --vus 5 --duration 5m k6/TwitterGPTtest5sqlPOST.js
```

---

### Сценарий 4: Стресс-тест генерации контента (`TwitterGPTtest5sqlPOSTer.js`)
Агрессивная генерация контента: каждый VU логинится и сразу создает пачку из 3–50 твитов подряд. По умолчанию настроен как длительный soak-тест на 1 час для проверки утечек памяти, переполнения очереди сообщений и устойчивости воркеров модерации.

```bash
# Длительный soak-тест по умолчанию (~1 час 2 мин):
k6 run k6/TwitterGPTtest5sqlPOSTer.js

# Быстрый стресс-тест публикации контента (6 VU на 3 минуты):
k6 run --vus 6 --duration 3m k6/TwitterGPTtest5sqlPOSTer.js
```

## 📊 Метрики и пороги (Thresholds)

Все сценарии разделяют метрики по конкретным эндпоинтам с помощью тега `endpoint`:

| Тег `endpoint` | Целевой HTTP-метод и URI | Описание |
| :--- | :--- | :--- |
| `Login` | `POST /api/token` | Получение JWT токена |
| `tweets_page1` | `GET /api/tweets?limit=50&page=1` | Главная лента, первая страница |
| `tweets_page2` | `GET /api/tweets?limit=50&page=2` | Скролл ленты, вторая страница |
| `tweets_page3` | `GET /api/tweets?limit=50&page=3` | Скролл ленты, третья страница |
| `tweets_page4plus` | `GET /api/tweets?limit=50&page>=4` | Глубокий скролл ленты (пагинация с высоким offset) |
| `ProfileNameBio` | `GET /api/profiles/{id}` | Загрузка данных профиля пользователя |
| `ProfileFeed` | `GET /api/profiles/{id}/tweets` | Лента твитов конкретного автора |
| `Like` | `POST /api/tweets/{id}/likes/toggle` | Простановка / снятие лайка (Toggle) |
| `CreateTweet` | `POST /api/tweets` | Создание твита |

### Пороговые критерии прохождения:
* **`http_req_failed`**: `< 1%` ошибок (rate < 0.01).
* **`http_req_waiting` (TTFB)**: `p(95) < 10000ms`.
* **`http_req_duration{endpoint:...}`**: `p(95) < 10000ms` индивидуально для каждого из эндпоинтов.

## 🔍 Полезный мониторинг во время тестов

Во время прогона любого из сценариев рекомендуется отслеживать состояние системы:

```bash

# Логи фонового обработчика очереди (Messenger / AI-модерация):

docker stats
```
